## Постоянное пополнение Roadmap — правило без срока окончания

- Roadmap **не считается окончательным ТЗ**. Новые инструменты, функции, настройки, идеи, архитектурные решения и ошибки добавляются по мере обсуждения; отсутствие задачи в текущей версии не означает, что её нельзя предложить позднее.
- Каждое новое требование проходит статусы **Предложено → Обсуждается → Согласовано → В работе → Реализовано → Проверено** (либо Отложено / Отменено), с фиксацией результата и даты. Галочка [x] для завершённой задачи ставится **только после проверки**; промежуточная реализация отмечается отдельно.
- Перед реализацией формулировать затрагиваемые классы, интерфейсы, зависимости и ожидаемое поведение. После реализации сверять фактические правки со списком согласованных и проверять регрессии.
- **Непреходящий приоритет:** отдельные классы для новых значимых функций и отдельные модули для инструментов; не допускать роста гигантских Activity / файлов. Это правило не зависит от этапа или числа последующих расширений.
- Документ обновляется **при каждом значимом изменении**: добавленные требования, закрытые пункты, проблемы сборки, результаты тестов, новая ближайшая задача. Ранее согласованные требования сохраняются, пока пользователь не пересмотрит их явно.
- При переходе в новый чат начинать с чтения этого Roadmap и фактического состояния репозитория; не полагаться на память о последних сообщениях.

## Главный архитектурный принцип — ОБЯЗАТЕЛЬНО

**Новые инструменты, крупные функции и значимые дополнения реализуются отдельными классами и, когда оправдано, отдельными Gradle-модулями. Никаких огромных монолитных файлов или Activity, содержащих всю логику.** Интерфейс чата, провайдеры API, менеджер контекста, локальная память, RAG, саммаризация, кэширование, расчёт стоимости, настройки, шина инструментов и каждый будущий инструмент имеют собственные компоненты с чёткими интерфейсами.

- Класс отвечает за одну понятную задачу; UI не реализует сетевую работу, SQL, биллинг или поиск.
- Инструменты подключаются через стабильный контракт (интерфейс); другие модули не должны зависеть от деталей реализации инструмента.
- Каждая новая возможность: сначала список файлов/классов и контрактов, анализ совместимости, затем согласование и реализация.
- Обязательные проверки после правок: сборка, тесты, проверка затронутых функций и отсутствия регрессий. Не рефакторить попутно несвязанные части.
- Разделение на классы **не означает** один класс на каждый инструмент: сложные инструменты могут содержать много классов в одном собственном модуле.
- Крупные изменения проводить небольшими проверяемыми шагами.
- **Текущий экспериментальный MainActivity.java монолитный и этому правилу не соответствует. Его безопасное разделение — приоритет до развития приложения.**

## Цель первой версии

Нативное Android-приложение — обычный ИИ-чат (без агента) с минимальными расходами на API, универсальными подключениями моделей, русским/английским интерфейсом и практически неограниченной локальной историей. Для генерации, эмбеддингов и саммаризации используются только API; на телефоне остаются хранение, FTS и поиск по сохранённым векторам. Модули будущего агента включаются в общий APK при очередном релизе; шина заранее проектируется расширяемой.

## UX и настройки

- Слева вверху — боковая панель диалогов, по центру название, справа индикатор контекста и «Информация о чате».
- Внизу ввод, прикрепление текста/файла/изображения и отправка.
- Информация о чате: индивидуальные настройки циклов (ориентир 5 по умолчанию), бюджет токенов, порог компактизации (ориентир 80%), RAG, глобальная статистика.
- Индикатор-кольцо показывает долю рабочего контекста перед API-запросом. После успешного сжатия показывает оставшуюся **реальную** заполненность, не искусственный ноль.
- Статистика по отдельному сообщению **не нужна** в первом релизе.
- Ручная стоимость на 1 млн токенов для модели у конкретного провайдера: обычный вход, выход, чтение кэша, запись кэша (если отдельно тарифицируется); стоимости сохраняются вместе с запросами; не пересчитываются задним числом.

## Известные ограничения текущего кода

- Монолитная Java MainActivity нарушает архитектурный принцип; в первой же итерации после сборки разнести ответственность на независимые классы.
- Векторный RAG и API-эмбеддинги отсутствуют; сейчас только простейший FTS4.
- Сжатие, оценка токенов и логика ограничения контекста экспериментальные и могут работать некорректно на настоящих длинных диалогах.
- API-ключ хранится в обычных app-private SharedPreferences, пока без отдельного шифрования.
- Нет изображений/PDF, streaming, полного мультиязычного интерфейса, нативных API адаптеров и тестов на устройстве.
- Workflow использует обычную временную debug-подпись runner: переустановка сборок может потребовать удаления приложения (потеря данных). До решения не хранить критичную переписку.
